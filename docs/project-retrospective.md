# RepoLens 项目复盘

## 一句话结论

RepoLens 验证了“对 GitHub Issue 提供独立 AI 分析页面”这一产品假设，但真实使用表明它相对于直接询问大模型或交给 Coding Agent 执行，没有形成足够强的用户优势。因此项目在 v0.5 完成可靠性、成本、评测和部署收尾后停止扩展，并保留为 AI 应用工程案例。

## 1. 最初假设是什么

最初假设包含三个判断：

1. 开发者面对陌生仓库时，很难快速把 Issue 与相关文件联系起来。
2. Coding Agent 可以先完成仓库搜索与问题拆解，降低人工阅读成本。
3. 将仓库概览、Issue 排名和实施建议集中在独立页面，会比用户自己在 GitHub 与聊天窗口之间切换更方便。

基于这些判断，第一版目标是：输入公开仓库 URL，先显示仓库结构和高优先级 Issue，再自动为排名靠前的 Issue 生成问题解释、实施步骤、测试方案和风险提示。

## 2. 为什么认为用户需要它

需求推断来自常见的代码接手过程：

- 新开发者不知道从哪个目录和文件开始阅读。
- Issue 经常只描述现象，没有给出实现位置。
- 仓库目录、Issue 内容和模型对话分散在不同界面。
- 通用聊天模型缺少主动获取仓库上下文的流程。

因此最初认为，一个把“仓库理解 → Issue 排名 → 相关文件 → 实施建议”串起来的页面，可以缩短进入问题的时间。

这个判断的问题是：它主要来自对工作流的想象，而不是对真实用户行为的验证。项目一开始没有先回答两个替代方案：

- 用户为什么不直接把任务交给 Hermes、Claude Code、Codex 等 Agent？
- 如果只需要建议，用户为什么不直接把 Issue 和代码复制给 DeepSeek？

## 3. 实际使用后为什么发现需求不成立

真实使用中，目标用户通常会选择两条更短路径。

### 路径 A：需要解决问题

直接把任务交给 Coding Agent。Agent 可以读取文件、搜索符号、修改代码、执行测试并提交结果。RepoLens 只提供一份建议，用户仍需回到 Agent 或 IDE 执行，增加了一次上下文切换。

### 路径 B：只需要理解问题

直接把 Issue 和关键代码交给 DeepSeek 等聊天模型，交互成本更低。对于小仓库或信息明确的问题，RepoLens 的检索、任务创建和页面展开并没有明显优势。

因此，独立 Issue 分析页面处于“聊天模型”和“可执行 Agent”之间，却没有在速度、准确性或工作流闭环上建立确定优势。功能存在不等于产品需求成立。

## 4. Hermes 出现了什么成本和可靠性问题

第一版把 Issue 分析作为普通 Hermes Agent 任务。端到端观察发现：

- 一次请求可能产生 18 次模型调用和 17 次工具调用。
- Hermes 会尝试 `web_search`、`web_extract`、浏览器、终端和 Skill 等工具。
- Issue 分析原本只需要依据给定文本和候选文件推理，却被扩展成开放式代理任务。
- 工具循环增加了延迟、Token、外部依赖和失败点。
- 最终输出可能包含 Markdown 包装、额外解释、截断内容或无效 JSON。
- Hermes 与后端并未宕机，但前端只能降级显示通用提示，用户感知为“不稳定”。

这说明问题不是模型不会回答，而是任务边界没有被系统约束。

### 真实 v0.5 观测

对 `open-webui/open-webui#27206` 的一次受控调用：

| 指标 | 结果 |
| --- | ---: |
| 耗时 | 26.03 秒 |
| 输入 Token | 18,173 |
| 输出 Token | 1,538 |
| 总 Token | 19,711 |
| 估算成本 | ¥0.021249 |
| 有效证据引用 | 2 条 |
| 结构完整性 | 完整 |

这次成本金额不高，但近两万 Token 说明代码上下文仍然是主要开销。成本也会随模型价格、仓库规模、Issue 数量和使用频率增长，因此不能只看单次金额。

## 5. 做了哪些工程优化

### 5.1 把 Agent 任务改成受控推理

Hermes 请求显式设置：

```json
{
  "tool_choice": "none",
  "tools": [],
  "reasoning_effort": "low",
  "max_tokens": 700
}
```

系统提示词禁止访问网络、调用工具和编造仓库事实，只允许使用传入的 Issue 与代码证据，并要求返回合法 JSON。

### 5.2 证据优先

系统先根据 Issue 关键词和仓库路径选择候选文件，再提取带行号的有限代码片段。模型输出只能引用已分配的证据 ID，后端会删除不存在的引用。

### 5.3 限制自动消费

最初排名前三的 Issue 自动分析，后来调整为只自动分析最重要的一条，其余必须由用户展开触发；用户还可以选择全部按需。

### 5.4 持久缓存与并发合并

缓存键包括：

```text
repository + issue_number + issue_updated_at + prompt_version
```

成功结果写入 SQLite，并保留内存热缓存。相同缓存键的并发请求共享一个任务。相同真实 Issue 的立即重复请求耗时从 26.03 秒降至 0.057 秒，不产生新的模型调用。

### 5.5 异步进度

同步接口继续兼容，同时增加后台任务与 SSE。前端可以显示缓存检查、获取证据、调用 Hermes 和完成/降级阶段，避免长请求表现为页面无响应。

### 5.6 失败降级与最小日志

连接失败、超时、无效 JSON、结构缺失都会返回安全降级结果。降级结果不缓存；日志记录失败类型、仓库和 Issue 编号，不记录密钥和完整 Issue 正文。

### 5.7 成本与评测

系统记录 Provider 返回的 Token usage，并通过可配置价格估算费用。固定回归集用于验证候选文件排序，第一次只有 60%，根据失败案例调整规则后达到 5/5。该结果只用于回归，不宣传为通用准确率。

### 5.8 可复现交付

补充固定依赖、Dockerfile、Compose、CI、34 项测试、Python/JavaScript/YAML 语法检查、敏感文件忽略规则和部署说明。

## 6. 最终为什么决定停止扩展

项目已经回答了可靠性与成本问题，但没有回答更重要的产品问题：

> 为什么用户要先在 RepoLens 看建议，而不是直接让 Coding Agent 解决？

继续加入注册、私有仓库、多租户、会员或更多页面，只会提高完成度，不会改变核心替代关系。为了避免用工程复杂度掩盖需求不足，v0.5 之后停止产品功能扩展。

停止扩展不等于项目失败。这个结论本身展示了完整的工程能力：

- 提出假设；
- 建立最小系统；
- 观察真实失败；
- 用数据定位成本与可靠性问题；
- 完成针对性改造；
- 重新判断用户价值；
- 在收益不足时停止继续投入。

## 哪些结论可以复用

1. 不要把所有 LLM 请求都设计成开放式 Agent 任务。
2. 工具能力越强，越需要明确任务边界和调用预算。
3. 模型输出必须与外部证据建立可校验关系。
4. `max_tokens` 不是总成本，输入上下文通常更值得优化。
5. 缓存必须包含数据版本和 Prompt 版本，失败结果不应长期缓存。
6. AI 功能应同时记录质量、延迟、失败率和费用。
7. 工程上可行不代表用户需求成立。

## 后续学习方向

下一步不继续包装 RepoLens，而是从零实现一个小型 Coding Agent Runtime，重点学习 Agent Loop、工具协议、权限分层、上下文压缩、任务恢复、循环检测、Git Worktree 隔离和成本评测。RepoLens 将作为“使用现成 Agent 后发现问题”的前置实验。
