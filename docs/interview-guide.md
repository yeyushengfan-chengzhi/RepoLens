# RepoLens 简历与面试手册

这份文档用于帮助项目作者准确表达已经完成的工作，不用于夸大项目准确率或商业价值。

## 简历项目名称

**RepoLens：证据约束与成本可观测的 GitHub Issue 分析系统**

## 简历描述（推荐版本）

> 基于 FastAPI、GitHub API、Hermes 与 DeepSeek 实现公开仓库 Issue 分析系统。针对通用 Agent 在简单分析任务中产生 18 次模型调用、17 次工具调用和无效 JSON 的问题，将流程重构为禁用工具的受控推理，并加入代码行级证据校验、异步任务与 SSE、SQLite 持久缓存、并发 single-flight、Token 成本遥测及安全降级。真实 Issue 调用耗时 26.03 秒、总计 19,711 Token；相同请求缓存命中耗时 0.057 秒且无新增模型费用。构建 34 项自动化测试和 5 个固定检索回归案例，并通过 Docker/CI 固化复现流程。

如果简历空间有限，可以拆成三点：

- 将开放式 Hermes Agent 任务重构为禁用工具、低推理、结构化 JSON 的受控调用，解决多轮工具滥用和输出不稳定问题。
- 实现行级代码证据、异步 SSE、SQLite+内存缓存、并发请求合并与故障降级，相同 Issue 缓存响应由 26.03 秒降至 0.057 秒。
- 建立 Token/成本遥测、34 项自动化测试和候选文件回归集，记录真实失败与产品假设不成立的复盘结论。

## 30 秒介绍

> RepoLens 是我做的一个 GitHub Issue 分析实验。最初我直接把 Issue 交给 Hermes，但一次简单分析实际触发了 18 次模型调用和 17 次工具调用，最后还可能不是合法 JSON。我把它改成了证据约束的单次推理：程序先筛选候选文件并提取带行号代码，模型只能根据这些证据返回结构化结果。系统还实现了异步进度、持久缓存、并发合并、成本监控和失败降级。项目最后也验证了独立 Issue 页面需求不够强，所以我在 v0.5 主动停止业务扩展，把它作为 Agent 可靠性和成本控制案例。

## 3 分钟介绍结构

### 1. 背景

陌生仓库中的 Issue 很难快速定位相关模块，因此最初希望用 Agent 自动搜索仓库并生成实施建议。

### 2. 第一次失败

Hermes 把只读分析当成开放式代理任务，调用搜索、浏览器、终端等工具。一次请求可能有 18 次模型调用和 17 次工具调用，耗时长且输出结构不稳定。

### 3. 核心设计

- 候选文件和证据由确定性代码负责；
- 模型只负责有限推理；
- 禁用全部工具；
- JSON、长度和证据 ID 由后端验证；
- 异步任务通过 SSE 展示进度；
- SQLite 缓存与 single-flight 降低重复成本；
- 超时和无效内容安全降级。

### 4. 数据

真实 Issue 一次调用 26.03 秒、19,711 Token、估算 ¥0.021249；相同请求缓存读取 0.057 秒且不调用模型。候选文件回归集第一次只有 60%，修正规则后固定 5 个案例全部命中。

### 5. 反思

工程问题得到解决，但产品没有证明比直接使用 Coding Agent 更方便。因此没有继续加入注册、多租户等外围功能，而是保留为工程案例。

## 高频面试问题

### Q1：为什么不直接调用 DeepSeek？

直接调用适合一次性问答。RepoLens 实验的是输入边界、代码证据、结构校验、缓存、并发、降级和成本记录。但项目也承认：对于普通用户，直接调用 DeepSeek 可能更短，这正是停止产品扩展的原因。

### Q2：为什么还要经过 Hermes？

项目最初基于已有 Hermes Provider 配置，希望复用统一模型网关。实测发现 Hermes 的默认 Agent 行为不适合这个受限任务，因此通过 OpenAI-compatible 参数关闭工具。后续系统也可以抽象 Provider，直接调用模型 API。

### Q3：`max_tokens=700` 为什么总 usage 仍然接近两万？

因为总 usage 包含输入上下文，代码证据和 Issue 占主要部分；部分 Provider 还会在 completion usage 中计入其内部推理。`max_tokens` 不是总账单上限，最终以 Provider 返回的 usage 为准。

### Q4：为什么只自动分析一个 Issue？

排名后的 Issue 不一定都会被用户查看。自动分析前三条会把可能无用的请求直接转化为费用，因此默认只分析价值最高的一条，其余由展开动作触发，也支持全部按需。

### Q5：如何防止缓存脏数据？

缓存键加入 Issue 的 `updated_at` 和 Prompt 版本。Issue 更新或输出协议变化后会自然产生新键。失败降级不缓存。

### Q6：为什么需要内存和 SQLite 两层缓存？

内存层减少同进程序列化和磁盘访问；SQLite 让成功结果在服务重启后继续存在。single-flight 解决缓存未命中时的并发重复调用。

### Q7：如何保证模型没有编造代码？

不能保证模型绝不编造，但可以缩小风险：只提供有限证据、要求返回证据 ID、后端过滤不存在的 ID，并在 UI 展示原始代码行。当前仍缺少逐句事实一致性评测，因此 README 没有声称完全消除幻觉。

### Q8：SSE 断开怎么办？

分析任务与 SSE 连接解耦。客户端断开不会取消后台任务，用户可以通过任务状态接口重新查询。当前活动任务是进程内状态，服务重启后需要重新请求。

### Q9：为什么不用向量数据库？

当前目标是验证受控流程，小型公开仓库下路径和关键词规则更透明、成本更低，也便于建立可解释基线。5 个案例太少，不能证明启发式优于向量检索。只有扩大真实评测集后，才有依据引入 embedding、reranker 或代码图。

### Q10：这个项目最大的失败是什么？

一开始先做了解决方案，后验证用户需求。真实使用表明独立 Issue 分析页面不如直接 Coding Agent 路径短。技术上完成不代表产品成立，这是项目最重要的复盘结论。

### Q11：为什么不做注册登录？

当前是本地单用户实验。注册会引入身份、Session、密码存储、权限隔离和数据合规，但不能验证核心假设，因此明确不做，而不是用简单登录页面包装“企业级”。

### Q12：下一步学什么？

从零实现小型 Coding Agent Runtime，理解 Agent Loop、工具协议、权限控制、上下文压缩、任务恢复、循环检测和 Git Worktree 隔离，并用 Hermes 作为对照。

## 可以主动展示的代码

- `backend/app/hermes.py`：模型请求约束、JSON 提取、错误分类和 Token 成本。
- `backend/app/evidence.py`：路径安全、代码片段和证据行号。
- `backend/app/storage.py`：持久缓存与 LRU。
- `backend/app/main.py`：后台任务、single-flight 和 SSE。
- `backend/tests/test_hermes.py`：模型异常、结构和并发测试。
- `evaluation/cases.json`、`scripts/evaluate.py`：可复现评测。

## 不应该声称的内容

- 不要说“准确率 100%”。只能说 5 个固定回归案例当前全部通过。
- 不要说“企业级 SaaS”。当前没有多租户、私有仓库和生产任务队列。
- 不要说“完全解决模型幻觉”。当前只是通过证据和校验降低风险。
- 不要说“替代 Claude Code”。项目已经明确没有证明这一点。
- 不要把 Provider 估算费用说成真实账单。
- 不要说 Docker 已完成运行验证；当前开发机没有 Docker。

## 面试官继续追问时的原则

优先讲亲自观察到的数据、失败和代码位置。对于没有实现的能力直接说明边界，并解释为什么当时不做。这个项目的优势不是功能数量，而是你能够区分：模型能力、系统可靠性、成本优化和产品需求是四个不同问题。
